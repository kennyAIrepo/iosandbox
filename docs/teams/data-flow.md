# Data flow: what leaves each laptop, per return path

Research and drafting, not legal advice. Every row that carries a legal consequence is marked "to confirm with counsel" in `privacy-risk.md`. Retrieval dates are 2026-09-18 unless stated. File:line citations are against the scratchpad research tree (`research/...`) and the read-only repo (`C:/Users/hanna/iosandbox/...`).

Scope: the memo's architecture (`scratchpad/teams-pilot-plan.html`, section "The design": "tracks their own camera ... broadcasts a ~600 byte landmark packet at 30 Hz, and renders everyone's avatars"; section "The packet": pose 33 + hands 2x21 + face 52 blendshapes + head quaternion) and its five return paths. **Packet definition: `research/gaps/wire-protocol/hopeos-wire.md` section 2 (HAND_STREAM 0x30, written 2026-09-18 after the first pass of this gap) is authoritative and supersedes the memo's packet**; where a row below says "memo packet" it describes what was proposed, not what ships: B/local twin (BroadcastChannel or our ws relay), C1 virtual camera, C2 video-effect app, C3 ACS participant, D meeting-stage app + Live Share.

## 2. Path D: meeting-stage app + Live Share (hosted Azure Fluid Relay)

Each participant's Teams client loads our stage URL; each person tracks locally; Live Share syncs state (memo, section D). Hosted relay facts: "Any data sent or stored through Fluid containers created by Live Share's hosted Azure Fluid Relay service might be accessible for up to 24 hours, though in most cases it's deleted within six hours" and "Live Share supports a maximum of 100 attendees per session" (Live Share FAQ, ms.date 2025-01-23, updated 2026-04-01, retrieved 2026-09-18). The FAQ gives **no data-residency statement** for the hosted relay; the documented way to control region or retention is to bring your own Azure Fluid Relay: "Consider using a custom Azure Fluid Relay service connection if you: Require storage of data in Fluid containers beyond six hours ... Transmit sensitive data through the service that requires a custom security policy" (same page). Fluid signals "are not retained in the container" (`research/meeting-app/NOTES.md:8`), but `LiveState` values are container state.

## 6. Everything that is stored anywhere (the DPO's list)

1. **Azure Fluid Relay (Live Share, Path D)**: Live Share ids, presence, `LiveState` game values, WebRTC SDP/ICE JSON (IP addresses) if the RtcTransport-via-Live-Share path is used, and any landmark packet that lands in container state - "accessible for up to 24 hours ... in most cases deleted within six hours"; region not documented for the hosted relay. Design rule R4 keeps landmarks off `LiveState`.
2. **OpenAI (voice path)**: nothing by default - `/v1/audio/transcriptions` has no abuse-monitoring or application-state retention and is ZDR-eligible (OpenAI 'Your data' guide, retrieved 2026-09-19). The transcript comes back in the response and is discarded by our proxy.
3. **Anthropic (command path)**: command text and the scene snapshot (seat labels only after R6) for up to 30 days under the standard commercial policy, or not at rest under an organisation-level ZDR arrangement; `claude-opus-5` is ZDR-eligible (not a Covered Model). R23 makes the retention configuration a deployment checklist item.
4. **Vercel (our origin)**: function invocation logs (metadata; our handlers log no bodies).
5. **Azure Communication Services (Path C3)**: identity directory entries, Azure Monitor logs with identities and call metadata; last chat message copy if chat is used.
6. **The pilot tenant (all Teams paths)**: RSC/app consent records, meeting attendance, and recordings/transcripts of anything rendered into a tile, under the tenant's own retention.
7. **The participant's browser**: consent record and settings in `localStorage`; MediaPipe model files in the HTTP cache.
8. **Our WebSocket relay**: nothing (in-memory fan-out only).
9. **CDN access logs** (Google Cloud Storage for `.task` models, jsDelivr for `tasks-vision` and three.js): IP address and user agent on page load; self-hosting (see `licences.md`) removes these recipients.

Nothing in the stack writes landmarks, frames, or audio to disk on the server side. There is also no server-side "session replay"; the only replay artefacts are the recorded test clips used by `CompositeCam.useFile` (`multi-person.md:44`), which are engineering fixtures and must not contain pilot participants.
