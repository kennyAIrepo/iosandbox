## 1. What the surface is

A "video filter" app is a Teams meeting app whose manifest declares `meetingExtensionDefinition.videoFilters[]` + `videoFiltersConfigurationUrl`. Teams lists the filters' thumbnails in **More actions > Video effects and settings**; selecting one loads the app's page in the meeting **side panel** and, from then on, the host hands the app every outgoing camera frame and puts whatever the app returns on the wire. ([support page](https://support.microsoft.com/en-us/office/apply-video-filters-in-microsoft-teams-meetings-c04a1326-7f63-4170-a4f7-0778520af465); [sample manifest](https://raw.githubusercontent.com/microsoft/teams-videoapp-sample/main/manifest/manifest.json))

The client-side API is the TeamsJS `videoEffects` module (package `@microsoft/teams-js`, current release **2.56.0, 2026-09-02** per [CHANGELOG](https://raw.githubusercontent.com/OfficeDev/microsoft-teams-library-js/main/packages/teams-js/CHANGELOG.md)). The Learn reference stamps every function: *"This API is in Beta and provided as a preview for developers and may change based on feedback that we receive. Do not use this API in a production environment."* ([videoEffects module](https://learn.microsoft.com/en-us/javascript/api/@microsoft/teams-js/videoeffects?view=msteams-client-js-latest), ms.date 2024-03-27, updated 2024-12-18). The source is marked `@beta` at module level ([videoEffects.ts L1-5](https://raw.githubusercontent.com/OfficeDev/microsoft-teams-library-js/main/packages/teams-js/src/public/videoEffects.ts)).

## 2. Which hosts support which mode

`registerForVideoFrame` chooses:

* **mediaStream** when `runtime.supports.video.mediaStream` is set **and** `window.chrome.webview.getTextureStream` + `registerTextureStream` exist (`isTextureStreamAvailable`, videoEffects.ts L437-449). Those two functions are the JavaScript side of **WebView2's TextureStream API**, an *experimental* API "shipped with our prerelease SDK" (Win32 prerelease 1.0.1724+), gated per origin by `ICoreWebView2ExperimentalTextureStream::AddAllowedOrigin(origin, allowWebTexture)`; the host must answer a `getTextureStream` request "within 10s" ([ICoreWebView2ExperimentalTextureStream](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2experimentaltexturestream?view=webview2-1.0.2194-prerelease)). So mediaStream mode = **new Teams on Windows (WebView2)**. The SDK builds `MediaStreamTrackProcessor → TransformStream → MediaStreamTrackGenerator` and registers the generator back with `registerTextureStream(streamId, generator)` ([videoEffectsUtils.ts L73-171](https://raw.githubusercontent.com/OfficeDev/microsoft-teams-library-js/main/packages/teams-js/src/internal/videoEffectsUtils.ts)). Your returned frame is re-wrapped as `new VideoFrame(yours, {timestamp: original.timestamp})` and **both** frames are closed by the SDK (L188-208).
* **sharedFrame** otherwise. It is the default for hosts that do not send a runtime config: `versionAndPlatformAgnosticTeamsRuntimeConfig.supports.video = { sharedFrame: {} }` ([runtime.ts L384-427](https://raw.githubusercontent.com/OfficeDev/microsoft-teams-library-js/main/packages/teams-js/src/public/runtime.ts)). This is the classic (Electron) Teams path and the path the sample's Electron test app drives: the host posts an NV12 `Uint8ClampedArray` you edit **in place** and you call `notifyVideoFrameProcessed()`.

**Official capability matrix contradicts the code.** The Learn "TeamsJS support across Microsoft 365" page (ms.date 2024-07-11, updated 2026-05-29) lists `video` as *Preview* with ticks **only** under Teams Android and Teams iOS — nothing for Teams desktop, new Teams desktop, or web — and then adds *"The following methods aren't supported on the Teams mobile client: video.notifySelectedVideoEffectChanged, video.registerForVideoEffect"* ([teamsjs-support-m365](https://learn.microsoft.com/en-us/microsoftteams/platform/m365-apps/teamsjs-support-m365)). Taken literally that leaves no host that supports the full API. The source code (WebView2 dependency, Electron shared frame) and the sample-repo issue below both indicate desktop is where it runs. Treat the matrix row as unreliable; ask the Teams contacts.

Browser requirements for the mediaStream path (mdn/browser-compat-data, fetched 2026-09-18, in `_src/bcd_*.json`): `MediaStreamTrackProcessor` Chrome 94 (partial: "Exposed on `Window` instead of `DedicatedWorker`"), Safari 18, Firefox none; `MediaStreamTrackGenerator` Chrome 94 only, `experimental: true, standard_track: false`; `VideoFrame` Chrome 94 / Firefox 130 / Safari 16.4; `VideoFrame.copyTo` `format` option Chrome 127. Chromium-only, which matches the WebView2 host.

## 3. Frame budget rules

* *"We require the frame rate of the video to be at least 22fps for 720p, thus the callback should process a frame timely."* (videoEffects.ts L128, L162) → **≤ 45 ms per frame at 1280×720**, serial (the SDK awaits your promise before reading the next frame).
* `VideoPerformanceMonitor.frameProcessTimeLimit = 100` ms by default; the host may override via `video.setFrameProcessTimeLimit`. Every second, if the average handler time exceeds the limit the SDK reports `video.performance.frameProcessingSlow` to the host ([videoPerformanceMonitor.ts L31-84](https://raw.githubusercontent.com/OfficeDev/microsoft-teams-library-js/main/packages/teams-js/src/internal/videoPerformanceMonitor.ts)). The timer is driven from frame arrivals (`VideoFrameTick`), not `setTimeout`.
* `videoEffectsEx` adds a hard **2000 ms** per-frame timeout that sends `notifyError("Frame not processed in 2000ms", 'warn')` (videoEffectsEx.ts L36, L295-303).
* *"When the failures accumulate to a certain number, the host will see the app is 'frozen' and ask the user to close it or not."* (L130) — the number is host-defined.
* Measured with this folder's harness (Chrome 152.0.7977.83 headless, fake camera capped at 20 fps, debug overlay only, no tracker). Draft-pass numbers in the table; the finisher re-run (2026-09-18 afternoon, same Chrome) was faster — 360p: A-mediaStream 3.5/12.7, A-sharedFrame 3.2/8.9, B-sharedFrame 2.6/22.2, B-mediaStream app-side avg 4.8–7.0 max 18.5; 720p: A-mediaStream 8.7/18.5, A-sharedFrame 9.7/16.9, B-sharedFrame 9.8/24.8, B-mediaStream app-side avg 8–10.5 max 24.4 ms. Both runs sit inside the 45 ms budget with no inference; plan with the slower (draft) figures:

| mode | 640×360 avg / max | 1280×720 avg / max |
|---|---|---|
| A in-process mediaStream | 6.9 / 18.9 ms | 15.3 / 28.0 ms |
| A in-process sharedFrame (NV12 via canvas readback + JS convert) | 6.7 / 11.9 ms | 14.0 / 44.2 ms |
| B real SDK mediaStream (app-side HUD) | 5–7 ms | 13–18 ms |
| B real SDK sharedFrame (host round trip) | 7.0 / 20.9 ms | 10.7 / 28.1 ms |

The NV12 path is the expensive one because `VideoFrame.copyTo(..., {format:'NV12'})` fell back to canvas conversion in Chrome 152 (the harness logs `nv12 via canvas`); the sample avoids this with a WebGL NV12 shader ([webgl-video-filter.js](https://raw.githubusercontent.com/microsoft/teams-videoapp-sample/main/src/webgl-video-filter.js)). A MediaPipe hand model will add ~10–30 ms on top, so **run inference in a Worker and skip frames** to stay under 45 ms.

## 4. The sample and its test app

Repo [microsoft/teams-videoapp-sample](https://github.com/microsoft/teams-videoapp-sample): 15 stars, last functional commit 2022-10-19 ("remove test app with readme"), only CI-pinning commits in 2026.

* `src/index.js` is written against the **pre-2.12 API**: `import { app, video } from "@microsoft/teams-js"`, `video.registerForVideoFrame(videoFrameHandler, { format: "NV12" })` with a single in-place handler; `yarn.lock` pins `@microsoft/teams-js@2.2.0`. The `video` namespace was renamed `videoEffects` in **2.16.0** and the two-handler `registerForVideoFrame` arrived in **2.12.0** (CHANGELOG). The sample therefore does not build against current TeamsJS without the rewrite in this folder's `video-effect.html`. A PR "update teamsjs sdk to 2.14.0" has been open since 2023-08.
* Dev server: Vite with `vite-plugin-mkcert`, `server.https: true`, base `/teams-videoapp-sample/app/` ([vite.config.js](https://raw.githubusercontent.com/microsoft/teams-videoapp-sample/main/vite.config.js)) — HTTPS is required because standard TeamsJS origin validation only accepts https ([validOrigins.ts L145-150](https://raw.githubusercontent.com/OfficeDev/microsoft-teams-library-js/main/packages/teams-js/src/internal/validOrigins.ts)). Origins you pass to `app.initialize([...])` are exempt: *"User provided additional valid origins take precedence as they do not require https protocol"* (L136) — that is how the harness runs on `http://localhost`.
* **Test app**: an Electron desktop program, "Test App 1.0.5" builds of 2023-01-13 on Electron 16.2.8 / 19.1.8 / 21.3.3, Windows x64 portable zip (~115–125 MB) and macOS x64/arm64 (Electron 16 build only), each with a `Video.Extensibility.Test.Application.EULA.docx` ([releases](https://github.com/microsoft/teams-videoapp-sample/releases)). Workflow per README: paste the app URL into "Video app url", Load; camera preview left, app panel right; click a thumbnail to apply. Tools: "Real-time Evaluation" / "Full Evaluation" of time-per-frame and memory (average, range, distribution), and "Reduce the resolution by half / Same / Double" ([README](https://raw.githubusercontent.com/microsoft/teams-videoapp-sample/main/README.md)). Being Electron, it exercises the **sharedFrame** buffer path only; it cannot exercise WebView2 mediaStream.
* Open issues nobody from Microsoft has answered: [#23](https://github.com/microsoft/teams-videoapp-sample/issues/23) (2024-10-17) test app on macOS shows black video; [#24](https://github.com/microsoft/teams-videoapp-sample/issues/24) (2025-07-01) *"This sample is completely broken in current MS Teams (25163.3607.3759.8168) ... the filters appear under the filters section, but selecting them causes an infinite spinner ... This definitely still works in the repo provided test app, but maybe it broke in the move from Electron to WebView2."* The same user notes Snapchat and Maybelline filters do work in their client.

## 5. `videoEffectsEx` — is it different?

Yes. It lives in `packages/teams-js/src/private/videoEffectsEx.ts`, stamped `@hidden @internal — Limited to Microsoft-internal use`, and has **no Learn page** (`.../teams-js/videoeffectsex` returns HTTP 404). It is still exported from the package (`private/index.ts: export * as videoEffectsEx`) so it is technically callable, but hosts decide whether to honour it. Extras over the public module ([videoEffectsEx.ts](https://raw.githubusercontent.com/OfficeDev/microsoft-teams-library-js/main/packages/teams-js/src/private/videoEffectsEx.ts)):

* `VideoFrameConfig.requireCameraStream?: boolean` — "Flag to indicate use camera stream to synthesize video frame or not. Default value is true." (L61-71). With `false` the app synthesises frames without a camera — the "audio-driven avatars" feature added in 2.3.0 (CHANGELOG L908).
* `VideoFrameConfig.audioInferenceModel?: ArrayBuffer` — "Machine learning model to run in the host to do audio inference for you" (L72-80); the result arrives per frame as `audioInferenceResult?: Uint8Array` (L100-110, L148-158).
* `VideoFrameConfig.requiredCapabilities?: string[]` and `VideoFrameData.attributes?: ReadonlyMap<string, Uint8Array>` (2.26.0; CHANGELOG: "still awaiting support in one or most host applications").
* `metadataInTexture` streams: the NV12 texture carries a 2-row `oti1` header and trailing metadata streams (`1dia` audio inference, attribute id map) that `TransformerWithMetadata` parses (videoEffectsUtils.ts L211-490).
* `notifySelectedVideoEffectChanged(type, id, effectParam?)`, `registerForVideoEffect((id, effectParam?) => …)`.
* `updatePersonalizedEffects(PersonalizedEffect[])` → `video.personalizedEffectsChanged` (L391-428) — the app can push its own thumbnail list to the client at run time (public apps can only list filters statically in the manifest).
* `notifyFatalError(msg)` → `ErrorLevel.Fatal`: "The host will stop the video pipeline and terminate this session" (L483-499).
* 2 s per-frame timeout (L36).

The monorepo's test app exercises both modules: `apps/teams-test-app/src/components/VideoEffectsApis.tsx` and `.../privateApis/VideoEffectsExAPIs.tsx` (copies in `_src/`).

## 6. Beta / deprecation / store / admin status (as of 2026-09-18)

* **API**: beta since the sample's 2022 birth; still `@beta` in 2.56.0 (2026-09-02). Changes since 2.26.0 are telemetry and tests only (e.g. "test: cover createEffectParameterChangeCallback", 2026-08-26). No deprecation notice anywhere in the source or Learn.
* **Manifest / store**: `videoFilters` and `videoFiltersConfigurationUrl` exist **only in the developer-preview schema**. Verified two ways: the DevPreview schema defines them (`_src/schema_DevPreview.json` L1013-1043) while the GA schemas v1.16, 1.17, 1.19–1.25 from `developer.microsoft.com/json-schemas/teams/` (`_src/ga_v1.*.json`) contain zero occurrences; and the Learn manifest reference (ms.date 2026-08-11) shows `videoFilters` / `videoFiltersConfigurationUrl` under moniker `m365-app-prev` only, absent from 1.19–1.30 ([root.meetingExtensionDefinition](https://learn.microsoft.com/en-us/microsoft-365/extensibility/schema/root-meeting-extension-definition?view=m365-app-1.30)). Consequence: a video-filter app **cannot be submitted to the store** (store validation uses GA schemas) and must be **sideloaded**: devPreview manifests "can't use Developer Portal for Teams ... To upload your app in Teams, select Apps > Manage your apps > Upload an app" and the tenant must allow custom app upload ([Public Developer Preview](https://learn.microsoft.com/en-us/microsoftteams/platform/resources/dev-preview/developer-preview-intro), updated 2025-12-19). The RSC strings `CameraStream.Read.User` ("Read the user's camera stream.") / `OutgoingVideoStream.Write.User` ("Modify the user's outgoing video.") come from the sample manifest (commit "update filters and videoAppContentUrl fields in the manifest (#17)", 2022-09-15) and **are** documented in the Learn RSC reference, user-scope delegated table (`_src/rsc.md` L171, L175; ms.date 02/20/2025). Mechanical proof of the schema split: `_tools/validate-manifest.cjs` passes `manifest.json` against DevPreview (draft-04, ajv-draft-04); against GA v1.25 ajv rejects `/meetingExtensionDefinition` for additional properties `videoFilters` and `videoFiltersConfigurationUrl` (and top-level `packageName`).
* **Admin gating**: end-user video filters ship through Microsoft's first-party **Custom Filters** app (public preview Jan 2023, GA rollout Feb–Apr 2023). "Video effects are built on the Teams platform infrastructure and can also come from partners ... No partner effects are in the preview: the 32 available are all from Microsoft"; admins "block the app completely or allow selective users ... with an app permission policy"; enabled by default for commercial/GCC, disabled in EDU; users must consent to camera-stream processing ([Office 365 IT Pros, 2023-01-23](https://office365itpros.com/2023/01/23/teams-video-effects/); [Teams blog, 2023-03-13](https://techcommunity.microsoft.com/blog/microsoftteamsblog/introducing-video-filters-in-microsoft-teams-meetings/3764187)). A third-party filter app is just another Teams app: it is governed by the tenant's app permission/setup policies and custom-app-upload switch. The `VideoFiltersMode` meeting policy (`NoFilters | BlurOnly | BlurAndDefaultBackgrounds | AllFilters`) governs **background effects**, not filter apps ([Set-CsTeamsMeetingPolicy](https://learn.microsoft.com/en-us/powershell/module/microsoftteams/set-csteamsmeetingpolicy)). Support page: "The custom filters app does not collect or process any biometric data or any data that identifies you" ([support](https://support.microsoft.com/en-us/office/apply-video-filters-in-microsoft-teams-meetings-c04a1326-7f63-4170-a4f7-0778520af465)). A Dec 2024 Q&A asking for org-built custom filters got "I didn't see any article or information from Microsoft for specific plans" ([Q&A](https://learn.microsoft.com/en-us/answers/questions/4420422/custom-filters-for-microsoft-teams-meetings)).
* **Third-party filter apps in new Teams (2025-2026)**: I found **no** Microsoft announcement, roadmap item or message-center post that either retires or reaffirms third-party video-filter apps. Signals: no Learn how-to page for building video apps exists (only the API reference and the sample); the sample is unmaintained; issue #24 (July 2025) reports the sample's filters listed but never applying in new Teams 25163; the capability matrix is inconsistent. Conclusion: the surface is **alive in the SDK, dead in the docs, unknown in the client** — it needs a live probe in a dev tenant (see §8).
* **Together mode custom scenes**: retired. MC1296478 (published 2026-04-30): "Retirement will begin in early June 2026 and is expected to complete by late June 2026"; removed: the Together mode View-menu option, "Custom Together mode scenes" and "seat assignment"; "The gallery view will be the primary multi-participant layout"; "No admin action is required" ([MC1296478](https://mc.merill.net/message/MC1296478); [Office 365 IT Pros 2026-05-04](https://office365itpros.com/2026/05/04/together-mode-retirement/); [Teams blog](https://techcommunity.microsoft.com/blog/microsoft365insiderblog/goodbye-together-mode-hello-simplified-meeting-layouts-in-microsoft-teams/4519312)). The Learn manifest reference (2026-08-11) still documents `meetingExtensionDefinition.scenes` (max 5, `maxAudience` ≤ 50) and links to the custom-scenes guide, but that guide's URL (`/apps-in-teams-meetings/teams-together-mode`) now serves the Teams platform landing page — the doc has been pulled. `videoFilters` is the only remaining AR-ish meeting surface, and it is dev-preview only.

## 7. Harness verification log (what actually ran)

`node verify-harness.mjs` — Chrome 152.0.7977.83 headless, `--use-fake-device-for-media-stream`, page served by `serve.mjs` with COOP/COEP (`crossOriginIsolated=true`). All four modes PASS (frames flowing to the output `<video>`, zero `notifyError`):

* **A-mediaStream** 97 frames / 5 s at 20 fps (fake-camera cap), handler avg 6.9 ms @360p, 15.3 ms @720p.
* **A-sharedFrame** 98 frames, NV12 in place, 6.7 ms @360p / 14.0 ms @720p.
* **B-mediaStream** (real teams-js 2.56.0 in an iframe): `initialize` → `getContext` → `video.registerForVideoEffect` → `video.mediaStream.registerForVideoFrame [{"format":"NV12"}]` → host `video.setFrameProcessTimeLimit` + `video.startVideoExtensibilityVideoStream {streamId}` → shim `getTextureStream` → SDK `video.performance.textureStreamAcquired` → tile click → `video.videoEffectChanged ["EffectChanged", id]` → host `video.effectParameterChange [id]` → `video.videoEffectReadiness [true, id]` → `firstFrameProcessed` → `performanceDataGenerated` once per second. 151 relayed frames. Note: `MediaStreamTrackGenerator` is **not transferable** (postMessage throws `DataCloneError`), so the shim relays processed `VideoFrame`s instead.
* **B-sharedFrame**: same handshake with `runtime.supports.video.sharedFrame`; host pumps `video.newVideoFrame` with a SharedArrayBuffer-backed NV12 buffer, app edits in place, `video.videoFrameProcessed [timestamp]` returns; 149 frames, 10.7 ms @720p.

What the harness does **not** prove: that new Teams still surfaces third-party filters and still emits `video.startVideoExtensibilityVideoStream` for them (issue #24 says it may not), and WebView2's `AddAllowedOrigin` gating.

## 8. Implications for hopeOS

1. **Architecture**: keep the effect as a pure module (`effect-core.js`) with both handlers; run MediaPipe + three.js in a Worker with `OffscreenCanvas`, frame-skip to hold ≤ 45 ms at 720p; do NV12 on the GPU (port the sample's shader) — the JS conversion alone is 7–14 ms.
2. **MediaPipe input**: `@mediapipe/tasks-vision` latest on jsDelivr is now **1.0.1** (not 0.10.x); hopeOS pins **0.10.18** in `sdk/`. Both `.d.ts` copies are in `_src/`: `ImageSource = TexImageSource` (1.0.1 L1823; 0.10.18 L1935), which includes `VideoFrame`, and `HandLandmarker.detectForVideo(videoFrame: ImageSource, timestamp)` (1.0.1 L1008; 0.10.18 L1120). A WebCodecs frame can therefore be fed directly on the mediaStream path with no canvas copy. Keep 0.10.18 (the version the HoloHands rig was tuned on) and self-host wasm + .task on the validDomains origin.
3. **Teams-twin sandbox**: `host-harness.html` Mode B *is* a Teams host twin for this surface — it speaks the real protocol to the real SDK. Wrap the gallery/toolbar UI around it and reuse Mode A for fast iteration.
4. **Pass-the-ball across tiles is not a video-filter feature.** A filter only sees the local camera and only writes the local outgoing stream; there is no cross-participant channel in `videoEffects`.
