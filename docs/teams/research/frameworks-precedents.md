# Precedents for cross-window / cross-tile object passing and in-call games (verified 2026-09-18)

Ordered by how directly each one teaches "an object leaves one person's frame and arrives in another's". Each entry: what it is, link, what it teaches about **state ownership** and **handoff**.

## A. One scene across several browser windows (same machine)

### 1. bgstaal/multipleWindow3dScene (MIT, 18.9k stars)
- Repo: https://github.com/bgstaal/multipleWindow3dScene ("A quick example of how one can 'synchronize' a 3d scene across multiple windows using three.js and localStorage"); source: [`WindowManager.js`](https://raw.githubusercontent.com/bgstaal/multipleWindow3dScene/main/WindowManager.js), [`main.js`](https://raw.githubusercontent.com/bgstaal/multipleWindow3dScene/main/main.js).
- Mechanism (from the source): `WindowManager` keeps two localStorage keys, `"windows"` (array of `{id, shape, metaData}`) and `"count"` (id counter incremented in `init()`). Each window writes its own `getWinShape()` = `{x: window.screenLeft, y: window.screenTop, w: window.innerWidth, h: window.innerHeight}`; other windows hear it via `addEventListener("storage", (event) => { if (event.key == "windows") ... })`; `beforeunload` splices the window out. In `main.js` every window renders **all** cubes but shifts its world by `sceneOffsetTarget = {x: -window.screenX, y: -window.screenY}`, smoothed with `falloff = .05`, applied as `world.position.x = sceneOffset.x`; each cube sits at `win.shape.x + win.shape.w * .5`.
- What it teaches:
  - **Ownership by author, mirror by everyone.** Each window owns exactly one record (its shape) and only ever writes that record; everyone renders the union. No conflicts, no locks.
  - **A shared coordinate frame is the whole trick.** Objects live in screen-global coordinates; each viewer applies its own offset. For tiles inside one page the equivalent is "gallery-global coordinates, each tile applies `-tileRect.x/y`".
  - **Transport is a detail.** localStorage + `storage` events are same-origin only; issue #8 ("Suggestion : Channel Broadcast instead of locale storage") proposes `BroadcastChannel` ([issue](https://github.com/bgstaal/multipleWindow3dScene/issues/8)). Our twin uses `BroadcastChannel` for windows on one machine and WebSocket/WebRTC for remote.
  - **Nothing here is contested.** Each window owns its own cube, so no object ever has two writers. The moment a ball can be held by two hands you need an owner token (section D).

### 2. chunqiuyiyu/multi-window-pong-game (MIT)
- Repo: https://github.com/chunqiuyiyu/multi-window-pong-game ("Play pong game across multiple windows on the same origin using localStorage"; "screenX and screenY are used to calculate different window positions"; "Inspired by [bgstaal]").
- What it teaches: the first shared-object variant of the pattern (a ball that leaves one window and enters another). The README does not say which window simulates the ball; read the source before copying. It forces exactly our question: **who integrates the ball's physics when it is between windows?**

## B. Objects passed between people in a video chat

### 3. Facebook Messenger video-chat AR games, "Beach Bump" (2018-08-08)
- Source: [Meta Newsroom](https://about.fb.com/news/2018/08/get-your-game-on-challenge-your-friends-with-video-chat-ar-games-in-messenger/): "Don't Smile", "Asteroids Attack", with "passing a beach ball back and forth with 'Beach Bump'" and "Kitten Kraze" to follow; "You can play with up to six people at a time"; started by "tap the video icon ... Then simply tap the star button and select one of the AR games".
- What it teaches: the only mass-market shipped example of **an AR object handed between participants' video frames**. It lived in the effects menu, i.e. positioned as an effect, not a separate app, which is the positioning we want in Teams. Implementation details were never published; assume the platform owned the ball state since Messenger owned both clients. Consumer-only and no longer promoted.

### 4. Microsoft Teams Together mode (2020 to 2026-06-30)
- Sources: [Microsoft Source, 2020-07-08](https://news.microsoft.com/source/features/work-life/microsoft-teams-together-mode/): Mary Czerwinski (Microsoft cognitive psychologist): "I've seen people lean over and tap each other. I've seen people make eye contact with each other who weren't sitting near each other"; segmentation "removed a person from their video surroundings and superimposed them into another's background". Retirement: "On June 30, 2026, Teams Together Mode will be retired. Custom Together Mode and Scene Studio in the Teams Developer Portal will no longer be available" ([What's new](https://learn.microsoft.com/en-us/microsoftteams/platform/whats-new#deprecated)); reason: "reduces the number of available meeting layouts and allows Microsoft to focus development on the Teams gallery" ([MC1296478](https://mc.merill.net/message/MC1296478)).
- What it teaches: **shared geometry beats shared pixels.** No object was ever passed; the effect came from placing segmented people in one coordinate frame so a gesture toward a neighbour read as a gesture toward that neighbour. Our gallery should offer a "bench" layout (tiles edge-to-edge, consistent scale) so a thrown ball's trajectory is legible. Microsoft's stated reason for retiring it is a warning: a cross-tile layer must not require a new meeting layout; it must work in the normal gallery.

### 5. Zoom Immersive View (2021) and Zoom Layers immersive mode
- Sources: [Zoom blog 2021-04-26](https://www.zoom.com/en/blog/introducing-zoom-immersive-view/): "Our current scenes can accommodate up to 25 participants in a scene"; "hosts will have the option to automatically or manually place participants into a virtual scene"; "Zoom 5.6.3 or higher", "Windows and MacOS desktop clients". Layers: "Only a meeting host may set the rendering context to immersive"; `drawParticipant` with `cutout: "person"` ([Using the Layers API](https://developers.zoom.us/docs/zoom-apps/guides/layers-using-api/)); sample app [zoom/zoomapps-customlayout-js](https://github.com/zoom/zoomapps-customlayout-js) ("A simple podcaster Zoom App to demonstrate Immersive Mode through our Layers API", MIT).
- What it teaches: the **host owns the scene**; participants are layers. If a ball game were built on Layers, the host's app instance would be the natural physics owner and the others would mirror via `postMessage`, with no way to read hands. Confirms our twin needs its own frame path.

## C. Games inside enterprise calls (state-sync patterns, no video contact)

### 6. Microsoft Games for Work (2022-11-16, pulled 2024-05-24) and Teams Carnival (2023)
- Games for Work: [Microsoft 365 blog](https://www.microsoft.com/en-us/copilot/blog/2022/11/16/build-connections-with-games-for-work-a-new-microsoft-teams-app/): "Microsoft IceBreakers, Wordament, Minesweeper, and Solitaire", "from 2 to 250 players", "developed by Microsoft Casual Games, an Xbox Games Studio", enterprise and education, desktop and mobile. The post now reads "Updated May 24, 2024: The Games for Work pilot app for Teams is no longer available." It does not name a sync technology.
- Teams Carnival: [Educator Developer Blog](https://techcommunity.microsoft.com/blog/educatordeveloperblog/multiplayer-gaming-experiences-in-microsoft-teams-using-live-share-sdk/3951741) (the blog body would not render for me; the following is from search-engine snippets of that page and should be re-read by a human): UCL postgraduate students, summer 2023, Unity WebGL games embedded via react-unity-webgl in a React meeting app; "The application's Live Share SDK functionality was written inside the React web app"; Space Shooter and Trivia Race share "a synchronised scoreboard", while Might & Malice, Jenga and Balloon Bomb "are all turn-based, but all meeting participants see the same thing at the same time"; the team tested "fully synchronous games before concluding that latency issues would not provide acceptable user experience".
- Live Share primitives: `LiveState` ("Synchronize any JSON serializable `state` value"; `.set()` "will change the state for everyone in the session"), `LiveEvent` (`.send()`, `on("received", (event, local, clientId))`), `LivePresence` (`.initialize(customUserData)`, `.update(...)`, `presenceChanged`) ([capabilities](https://learn.microsoft.com/en-us/microsoftteams/platform/apps-in-teams-meetings/teams-live-share-capabilities)); samples Dice Roller, Agile Poker ([live-share-sdk README](https://raw.githubusercontent.com/microsoft/live-share-sdk/main/README.md)).
- What it teaches: on Teams, **one launcher joins the Fluid container**, each game gets its own DDS; ownership changes are `LiveState` writes, throws are `LiveEvent`s. The Carnival team's own conclusion (turn-based or scoreboard sync, not fully synchronous play) is the empirical latency verdict on Live Share: use it for *authority* (who holds the ball, score, goal tile), never for per-frame landmarks.

### 7. Zoom Apps games (2021) and Houseparty (2016 to October 2021)
- Zoom: launch release 2021-07-21, "There are over 50 Zoom Apps available now", "Heads Up! is a fun and hilarious game by Ellen DeGeneres" ([GlobeNewswire](https://www.globenewswire.com/news-release/2021/07/21/2266549/0/en/Zoom-Elevates-Platform-Experience-with-Launch-of-Zoom-Apps-and-Zoom-Events.html)); Kahoot! app for Zoom the same day ([Kahoot! press](https://kahoot.com/press/2021/07/21/kahoot-integrates-zoom-video-conferencing-virtual-learning/)). Houseparty: "group video chats with friends and even play games, like Uno, trivia, Heads Up and others"; acquired by Epic in 2019, shut down October 2021 ([TechCrunch 2021-09-09](https://techcrunch.com/2021/09/09/epic-games-to-shut-down-houseparty-in-october-including-the-video-chat-fortnite-mode-feature/)).
- What it teaches: panel games with their own backend are easy to ship and easy to ignore. Engagement came from the *video* (Heads Up! is a face-to-camera game) even though the app never touched the video. Our differentiator is closing that loop.

### 8. Google Meet add-ons co-doing and Discord Activities
- Meet: `broadcastStateUpdate(newState: CoDoingState)`; "This shared state is eventually consistent across participants"; "This binary state should be complete, not partial, as the Meet add-ons SDK doesn't provide guarantees around the delivery of individual messages"; "the Meet add-ons SDK selects a canonical winning update" ([reference](https://developers.google.com/workspace/meet/add-ons/reference/websdk/live_sharing_sdk.codoingclient.broadcaststateupdate)); the program is "closed to new signups" ([guide](https://developers.google.com/meet/add-ons/guides/use-CoDoingAPI)).
- Discord: "Activities are web apps hosted in an iframe that use the Embedded App SDK" ([overview](https://docs.discord.com/developers/activities/overview)); `ACTIVITY_INSTANCE_PARTICIPANTS_UPDATE`, `getInstanceConnectedParticipants()` ([Embedded App SDK](https://docs.discord.com/developers/developer-tools/embedded-app-sdk)); game state on your backend.
- What it teaches: both platforms ship the **"complete state, last-writer-wins" model**. For a ball with one holder that model is enough: the state is `{holder, pos, vel, t}` and the holder is the only writer.

## D. Multi-user AR state on device: Snap Connected Lenses
- Sources: [Connected Lenses overview](https://developers.snap.com/lens-studio/features/connected-lenses/connected-lenses-overview) ("pass and store data between devices that are running the same Lens"; "This feature is only available for use in Spectacles and Camera Kit"); [Sharing data](https://developers.snap.com/lens-studio/features/connected-lenses/sharing-data) (page marked "Supported on: Spectacles"): `MultiplayerSession`, `CreateRealtimeStore` ("creates a GeneralDataStore that automatically syncs between all participants") with "the ability to configure the owner of the store", `CloudStorageModule`. Camera Kit *Web* support is not stated.
- What it teaches: Snap's model is **per-object realtime stores with a configurable owner**. That is the right granularity for props: one store per apple/ball, owner = the hand that wraps it.

## What the precedents say about ownership and handoff (design rules for the twin)

1. **Single writer per object.** Every working precedent (bgstaal's per-window records, Snap's owned RealtimeStore, Meet's canonical-winner rule) reduces to one writer per record. The ball has an `owner`; only the owner's client integrates physics and publishes `{pos, vel, t}`; everyone else interpolates.
2. **Handoff is a two-phase event, not a state write.** Throw: the owner publishes a `release` event with launch state and a target tile, and keeps simulating until an `accept`. Catch: the receiving client detects wrap/cradle per the prop doctrine and publishes `accept`; the old owner stops. If nobody accepts before the ball leaves the target's frame, ownership falls back to the "table" (server or host), which simulates gravity to the floor. This mirrors Live Share's `LiveEvent` (stateless) plus `LiveState` (holder) split.
3. **Shared coordinates are gallery coordinates.** Following bgstaal and Together mode, store ball position in a gallery-global frame (tiles laid out edge to edge, normalized to tile height) and let each client offset by its own tile rect. The tile layout must be identical for everyone (the twin server publishes it); the real Teams gallery does not guarantee this, which is a known gap for any real-Teams version.
4. **Video contact needs frames; state does not.** Every game that shipped in an enterprise call touched no pixels. Our cross-tile catch needs hand landmarks from the receiving client only (each client tracks its own camera), so landmarks never leave the machine; only the small `{holder, pos, vel}` state and the release/accept events cross the wire. That keeps the demo within the privacy posture of a Teams video filter (own camera, explicit consent).
5. **Host-controlled scenes die; per-user effects live.** Together mode (retired 2026-06-30), Zoom Immersive (host-only), Workrooms ("From February 16, 2026, you will no longer be able to access Workrooms", [Meta](https://www.meta.com/help/quest/2464765133873078/)), Mesh in Teams (retired 2025-12-01, [adoption.microsoft.com](https://adoption.microsoft.com/en-us/mesh/)), Games for Work (pulled 2024-05-24). What persists are per-user effects and stage apps. Design the ball game so each tile's rendering is its owner's effect, and the shared part is a stage-sized scoreboard and goal designation.
